# Plan 0001 — Foundation v0.1

Status: In progress

## Problem
A health knowledge project can become unsafe or incoherent if content growth starts before evidence boundaries, patient-data rules, AI authority, and contribution workflows are defined.

## Goal
Create a small but durable project constitution and architecture before scaling medical content.

## Scope
- mission and project boundaries;
- medical safety and privacy policy;
- governance/change classes;
- agent rules;
- evidence/content model;
- canonical-data architecture;
- user journeys;
- long-term roadmap;
- initial schemas, agent roles, and GitHub contribution templates;
- ACL/meniscus pilot placeholders.

## Non-goals
- comprehensive ACL or meniscus guidance;
- patient-data collection;
- MRI interpretation;
- production website;
- production chatbot;
- automated merging of medical content.

## Acceptance criteria
- A new contributor can tell where evidence, community experience, private patient data, and approved knowledge belong.
- An agent can tell what it may do autonomously and what requires human review.
- Medical-content changes have a defined review class.
- Website, database, GitHub, and AI responsibilities are documented.
- Later plans have explicit stage gates.

## Risks
The biggest early risk is false confidence: a polished repository can appear medically authoritative before content has been clinically/evidence reviewed. Pilot content must therefore expose status clearly.

## Exit
Foundation docs are merged to `main`, reviewed for internal consistency, and used as the baseline for Plan 0002.
